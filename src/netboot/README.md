# `src/netboot/` — the SAM-side Z80 netboot subsystem (Phase 3)

A standalone SAM Coupé Z80 program (separate from the `src/` assembler) that turns a SAM + Quazar Trinity into an aarch64 **netboot server**: it answers a Raspberry Pi's DHCP and TFTP requests so the Pi boots over the network from images the SAM holds. It also contains the TFTP **client** used to fetch images onto the SAM. It shares no memory map, paging trampoline, or build target with the assembler.

**Bootable programs** (the runnable artifacts, built to bootable SAM disks via `tools/build-disk -netboot`): `smoke_test.asm` is increment 1 (the Trinity bring-up smoke test); `netboot_server.asm` is increment 2 (the integrated DHCP + TFTP netboot server); `netboot_client.asm` is increment 3 (the TFTP client that fetches a `.mgt` and writes it to Trinity storage); `netboot_http.asm` is the HTTP-fetch capstone (fetch a firmware blob over HTTP and write it to Trinity storage). How to run them on real Trinity hardware: [`docs/notes/netboot-trinity-testing.md`](../../docs/notes/netboot-trinity-testing.md).

It sits on the trinload UDP/IP/Ethernet stack (simonowen/trinload, Simon Owen; BSD-style licence) and adds the DHCP responder (i86), TFTP server (i83) and TFTP client (i82) state machines.

## Authority and verification

The host Go module `tools/netboot-oracle/` is the **authority**: its `frame`/`dhcp`/`tftp` packages build and parse the same packets, verified byte-for-byte against masked golden vectors from a real Pi 400 capture. Each routine here is a faithful port of the matching Go function (memory `feedback_go_is_encoding_authority`) — port, do not reinvent.

The **protocol logic is host-verifiable**: `tools/netboot-oracle/z80/` assembles each routine with pyz80, runs it under a flat-memory koron-go/z80 harness, and asserts its emitted packet equals the golden vector (`make ci-netboot-z80`, the `netboot-z80` CI job).

The **ENC28J60 wire I/O is now host-verifiable too (i80)**: `tools/netboot-oracle/z80/enc28j60.go` emulates the Trinity microcontroller (port `&DC` select/busy, `&DD` identity probe) and the ENC28J60 SPI chip (port `&DE`: the RCR/WCR/RBM/WBM/BFS/BFC command set, the four register banks, the 8 KB RX/TX buffer, the MAC/MII read-dummy), grounded in the ENC28J60 datasheet (DS39662E) and the driver's own port usage. The test runs the *real* vendored driver (`encdrv.asm`) against it and asserts `drv_init` succeeds, `drv_write` puts a frame on the virtual wire byte-exact, and an injected RX frame comes back through `drv_read` byte-exact. This is **emulation verification, not hardware verification** — an **end-to-end Pi boot and real-silicon TX/RX remain gated on real Trinity hardware** (the final integration gate; `docs/notes/trinity-capabilities.md`).

## Files

- `build_udp_frame.asm` — originate a fresh UDP/IPv4/Ethernet frame (plan §5.1), the primitive trinload lacks; the port of `frame/frame.go::BuildUDPFrame`.
- `build_arp_request.asm` — originate a fresh Ethernet ARP request (plan §5.1, RFC 826) so the client learns the server's MAC before its RRQ; the port of `frame/frame.go::BuildARPRequest`.
- `build_arp_reply.asm` — originate a fresh Ethernet ARP reply (RFC 826), the inverse of the request: a unicast frame back to an asker announcing the SAM's MAC for its IP; the port of `frame/frame.go::BuildARPReply`. Used by the bring-up smoke test.
- `build_tcp_segment.asm` — originate a fresh TCP/IPv4/Ethernet segment (i70), the TCP analogue of `build_udp_frame`. TCP is the one new transport the firmware-self-provisioning HTTP client rides on (the rest of the stack is UDP-only); the new arithmetic vs UDP is the mandatory pseudo-header checksum (RFC 793). The port of `tcp/tcp.go::BuildSegment`.
- `sha256.asm` — SHA-256 (FIPS 180-4), streaming init/update/final — the firmware-download verify primitive (i100); also an i88 building block. Host-verified vs Go crypto/sha256 + NIST vectors.
- `hmac_sha256.asm` — HMAC-SHA256 (RFC 2104), the first i88 (on-SAM TLS) building block above SHA-256: TLS 1.3's HKDF key schedule (RFC 5869) is HMAC-SHA256. A thin orchestration over `sha256.asm` (`include`s it, no new hashing arithmetic) — prepares the block-sized key `K0` (zero-pad if ≤64, else SHA256-then-pad) and does the two `ipad`/`opad` passes. `hmac_sha256` reads the key/message parameter cells and writes the 32-byte MAC to `(HL)`. Standalone leaf — not in the bootable image. Host-verified vs Go `crypto/hmac` + `crypto/sha256` (`hmac_sha256_test.go`: the RFC 4231 vectors + the K0-branch boundaries — key <64 / ==64 / >64-hashed — + empty key/message).
- `hkdf.asm` — HKDF (RFC 5869) over HMAC-SHA256, the i88 TLS 1.3 key schedule. `hkdf_extract` (PRK = HMAC-SHA256(salt, IKM)) + `hkdf_expand` (OKM = `T(1)||T(2)||…` truncated to L, `T(i)=HMAC(PRK, T(i-1)||info||byte(i))`). Orchestration over `hmac_sha256.asm` — no new arithmetic. Standalone leaf — not in the bootable image. Host-verified vs Go `crypto/hkdf` (`hkdf_test.go`: the RFC 5869 Appendix-A vectors + multi-block-OKM + zero-salt/empty-info + the L boundaries 1/32/33/64).
- `hkdf_expand_label.asm` — TLS 1.3 HKDF-Expand-Label (RFC 8446 §7.1), the function the whole TLS key schedule is built from (every handshake/traffic secret + record key/IV is an Expand-Label). `expand_label` assembles the HkdfLabel (`uint16 length` + `"tls13 "+label` + `context`, each length-prefixed) into a buffer and calls `hkdf_expand` — no new arithmetic. Standalone leaf — not in the bootable image. Host-verified vs a Go RFC 8446 §7.1 reference, itself anchored to the independent RFC 8448 known-answer (TLS 1.3 Early-Secret + its "derived" secret), across the key-schedule labels (`derived`/`key`/`iv`/`finished`/traffic) with empty + 32-byte hash contexts (`hkdf_expand_label_test.go`). Derive-Secret is Expand-Label with context = the transcript hash — a later thin caller.
- `chacha20.asm` — the ChaCha20 block function (RFC 8439 §2.3), the first i88 cipher (a from-scratch ARX port — the only one of the suite that is new arithmetic, not orchestration). `chacha20_block(key, counter, nonce)` builds the 16-word state (`"expand 32-byte k"` || key || counter || nonce, little-endian), runs 20 rounds of the quarter-round on a working copy (the four rotates ROTL16/12/8/7 are built from byte permutes + single-bit rotates, since the Z80 has no 32-bit ops), adds the initial state word-wise, and serialises the 64-byte keystream. `chacha20_encrypt` is the stream cipher (RFC 8439 §2.4): XOR the keystream into the message one 64-byte block at a time, incrementing the block counter per block (so it both encrypts and decrypts). Standalone leaf — not in the bootable image. Host-verified vs the RFC 8439 known-answer vectors (`chacha20_test.go`: the block function vs §2.3.2 + Appendix A.1 #1/#2; the stream cipher vs the §2.4.2 worked example + an encrypt∘decrypt round-trip across the block boundaries).
- `poly1305.asm` — the Poly1305 one-time authenticator (RFC 8439 §2.5), the ChaCha20-Poly1305 MAC and the suite's second from-scratch arithmetic port. `poly1305_mac(key, msg)` clamps `r`, runs the `a = (a + n)·r mod 2^130−5` loop over each 16-byte block (`n` = the block bytes with a `0x01` appended, little-endian), adds `s`, and writes the low 16 bytes as the tag. The Z80 has no multiply, so everything is byte-radix big-integer: `mul8` is an 8×8→16 shift-add, `poly_mul_a_r` the 17×16 schoolbook product, and reduction mod 2^130−5 uses `2^130 ≡ 5 (mod p)` (split `P = low + 2^130·high`, replace with `low + 5·high`, fold until below 2^130); `poly_freeze` does the final conditional subtract of `p` so the tag is canonical before `+s`. Standalone leaf — not in the bootable image. Host-verified vs the RFC 8439 §2.5.2 known-answer vector + an independent `math/big` reference (`poly1305_test.go`: the KAT, then the reference across message lengths 0/partial/block-boundary/multi-block and edge-case keys incl. zero/max `r`).
- `x25519.asm` — Curve25519 field arithmetic over GF(2²⁵⁵−19), the foundation for the X25519 key exchange (RFC 7748) — the last and largest of the i88 from-scratch multi-precision ports (the Montgomery ladder + scalar mult build on this layer in a follow-up). Field elements are 32-byte little-endian, kept `< 2²⁵⁵` (almost-reduced); `fe_freeze` gives the canonical `< p` form. `fe_mul` is the centrepiece: `mul8` (8×8→16) → `fe_schoolbook` (the 32×32→64-byte product) → reduction via `2²⁵⁶ ≡ 38` (fold the high half in with ×38) then `2²⁵⁵ ≡ 19` (`fe_reduce33` folds any residual bit-255 overflow in with ×19 until `< 2²⁵⁵`). `fe_add`/`fe_sub` (the latter via `+2p` to stay positive) and `fe_mul121665` (the curve constant a24 = (A−2)/4, done as `fe_mul` by a constant) round out the set. Not constant-time (the reductions branch on data) — acceptable for this one-shot, content-hash-pinned firmware fetch (design §7). Standalone leaf — not in the bootable image. Host-verified vs a `math/big` reference mod 2²⁵⁵−19 (`x25519_field_test.go`: every op over edge operands — 0/1/p/p−1/2²⁵⁵−1/19/38/121665/random — byte-exact for `fe_freeze`, value-equal mod p for the almost-reduced ops, plus the `< 2²⁵⁵` output invariant; `fe_mul` covers max×max to exercise the full fold chain). `fe_invert` (the modular inverse a⁻¹ = a^(p−2) via Fermat) is also here — a faithful port of TweetNaCl's `inv25519` addition chain (square every step; multiply by the input except at chain positions 2 and 4) — host-verified by the defining property a·a⁻¹ ≡ 1 (mod p) and equality with `math/big`'s ModInverse (0 inverts to 0). It runs ~37M byte-ops, past the harness's default runaway guard, so it passes a raised per-call `StepCap` (a new optional `Entry` field). The `x25519(scalar, u)` entry (RFC 7748 §5) completes the key exchange: clamp the scalar, decode/mask u, run the Montgomery ladder (255 differential add-and-double steps via `ladderstep` + a constant-bit `cond_swap_state`, the field ops marshaled through `FE_A`/`FE_B`/`FE_OUT`), then return `x2 · z2⁻¹` (via `fe_invert`) frozen to 32 LE bytes — host-verified vs the RFC 7748 §5.2 KATs **and** Go `crypto/ecdh` over the base point (`x25519_test.go`). So **X25519 is complete** (field arithmetic + inversion + ladder).
- `aead.asm` — AEAD_CHACHA20_POLY1305 (RFC 8439 §2.8), the TLS 1.3 record-protection construction and the first brick toward the handshake. It composes the verified ChaCha20 + Poly1305 (`include`d; built with `-D NETBOOT_AEAD` so their `NETBOOT_STANDALONE` org guard stays inert and `aead.asm` sets the org once — the primitives' own builds are unchanged). `aead_encrypt`: `otk = chacha20_block(key,0,nonce)[0..32]`, `ct = chacha20_encrypt(key,1,nonce,pt)`, `tag = poly1305_mac(otk, AAD‖pad16‖CT‖pad16‖le64(lenAAD)‖le64(lenCT))`. `aead_decrypt` recomputes the tag, compares difference-accumulating (no early-out), and only then decrypts — setting `AEAD_OK` to 1 (authentic) or 0 (forged). Not constant-time (the primitives branch on data) — acceptable for the pinned one-shot fetch (design §7). Standalone leaf — not in the bootable image. Host-verified vs the RFC 8439 KATs (`aead_test.go`: §2.6.2 key-gen, §2.8.2 encrypt ciphertext+tag byte-exact, a decrypt round-trip across lengths 0…200 with/without AAD, and tamper rejection of a flipped tag/ciphertext/AAD byte). The TLS-1.3 handshake that composes these is spec'd in [`../../docs/specs/tls13-handshake.md`](../../docs/specs/tls13-handshake.md) as six host-verifiable bricks; the next files are those bricks.
- `tls_keyschedule.asm` — the TLS 1.3 key schedule (RFC 8446 §7.1), handshake **brick 1**: pure orchestration over the built `hkdf_extract` + `expand_label` (no new arithmetic). `tls_key_schedule` takes the X25519 ECDHE shared secret + the two transcript hashes (Hash(CH..SH), Hash(CH..serverFin)) and derives the whole secret tree — Early → derived → Handshake (+ c/s hs traffic) → derived2 → Master (+ c/s ap traffic) — plus each traffic secret's record `key`/`iv`/`finished` (via Expand-Label). Built with `-D NETBOOT_TLS_KS` (the `aead.asm` composition idiom; the include chain's `org` guard in `sha256.asm` stays inert). Standalone leaf — not in the bootable image. Host-verified vs a Go RFC 8446 §7.1 reference (Go `crypto/hkdf` + the §7.1 HkdfLabel encoding) across two input sets (`tls_keyschedule_test.go`), with the Early/derived secrets anchored directly to the RFC 8448 known-answer.
- `tls_record.asm` — TLS 1.3 record protection (RFC 8446 §5.2–5.3), handshake **brick 2**: the framing layer over the verified AEAD. `tls_record_seal` builds the per-record nonce (`iv XOR (zeros4‖seq_be64)`), the 5-byte TLSCiphertext header used as the AEAD AAD (`17 03 03` + the length), and the TLSInnerPlaintext (`content‖real_type`), then `aead_encrypt`s into a full record; `tls_record_open` reverses it — AEAD authenticity gates output, then it strips zero padding + the trailing content-type byte to recover `(content, type)` and sets `TR_OK`. The caller supplies the sequence number. Built with `-D NETBOOT_TLS_RECORD` (the composition idiom; `aead.asm` + the ciphers `include`d, their org guards inert). Standalone leaf — not in the bootable image. Host-verified (`tls_record_test.go`): a seal→open round-trip recovering `(content, type)` across types/lengths/seqs, an independent Go reconstruction of the §5.2/§5.3 framing fed through the verified Z80 `aead_encrypt` (byte-exact record), and tamper/wrong-sequence rejection.
- `tls_transcript.asm` — the TLS 1.3 handshake transcript hash (RFC 8446 §4.4.1), handshake **brick 5**: a thin wrapper over the verified `sha256.asm` streaming hash. `tls_transcript_init`/`tls_transcript_update` are the running SHA-256 over the concatenated handshake messages; `tls_transcript_snapshot` writes SHA-256(messages-so-far) to `(HL)` **without ending the stream** — it saves the 105-byte persistent SHA-256 state (`SHA_H`‖bitlen‖fill‖block), calls `sha256_final` into the output (which consumes the state by padding), then restores the state so later updates/snapshots continue. Derive-Secret takes such a snapshot as its key-schedule context. Built with `-D NETBOOT_TLS_TRANSCRIPT` (the composition idiom). Standalone leaf — not in the bootable image. Host-verified vs Go `crypto/sha256` (`tls_transcript_test.go`: an empty-transcript snapshot = SHA-256(""), then interleaved snapshots over a message sequence straddling the 64-byte block boundary, each = the hash of the concatenation so far, with the stream continuing after each snapshot).
- `tls_client_hello.asm` — the TLS 1.3 ClientHello builder (RFC 8446 §4.1.2), handshake **brick 3**: pure byte assembly (no crypto include'd). `tls_build_client_hello` emits the Handshake message (`client_hello` type ‖ uint24 length ‖ body) for our single fixed offer — `legacy_version`=0x0303, a supplied 32-byte random + 32-byte `legacy_session_id` (the middlebox-compat convention), one cipher suite (`TLS_CHACHA20_POLY1305_SHA256`), null compression, and five extensions: `server_name` (SNI, from `CH_HOSTNAME`), `supported_versions` (TLS 1.3 only), `supported_groups` (x25519 only), `signature_algorithms` (a fixed ECDSA/RSA-PSS/RSA-PKCS1 set), and `key_share` (one X25519 entry from the supplied ephemeral public key). The variable-length container lengths (handshake, extensions block, the nested SNI lengths) are emitted as placeholders and back-patched from the actual emitted positions, so they cannot drift from the content. The output bytes both feed the transcript and, wrapped in a plaintext record by the state machine (brick 6), go on the wire. No ALPN/PSK/early-data — the smallest conformant offer github completes (HTTP/1.1 is the no-ALPN default). Built with `-D NETBOOT_TLS_CH` (sets the org once). Standalone leaf — not in the bootable image. Host-verified (`tls_client_hello_test.go`): byte-identical to an independent Go reconstruction of the §4.1.2 framing across host-name lengths; parsed by Go `crypto/tls` into a `tls.ClientHelloInfo` with the expected ServerName / single cipher suite / TLS 1.3 / X25519 / signature schemes (the stdlib TLS implementation as an independent structural oracle, which also rejects a malformed message); and a hand-written TLV walk recovering the x25519 key_share = the supplied public key.
- `tls_server_flight.asm` — the TLS 1.3 server-flight parser (RFC 8446 §4.1.3/§4.3), handshake **brick 4**. Two functions over the server's 1-RTT response. `tls_parse_server_hello` validates a ServerHello and extracts the server's X25519 key_share: it sets `SH_OK`=1 only if the message is a `server_hello` (type 2) whose random is **not** the HelloRetryRequest sentinel (SHA-256("HelloRetryRequest") — we don't handle HRR, but offering x25519 means github won't send one), whose `cipher_suite` is `TLS_CHACHA20_POLY1305_SHA256` (0x1303), whose `supported_versions` selects TLS 1.3 (0x0304), and which carries a `key_share` for group x25519 (0x001d) with a 32-byte key (copied to `SH_SERVER_PUB`). `tls_walk_server_flight` walks the **decrypted** concatenated handshake flight that follows (`EncryptedExtensions`/`Certificate`/`CertificateVerify`/`Finished`; the caller reassembles records into one buffer): each message (`type ‖ uint24 length ‖ body`) is folded into the running transcript via `tls_transcript_update`, and **just before** the `Finished` is folded it snapshots Hash(CH..CertificateVerify) — the context for verifying the server Finished — into `SF_HASH_BEFORE_FIN`; the `Finished`'s verify_data is captured to `SF_FINISHED`, and `SF_OK`=1 iff all four expected messages were seen. The transcript must already hold ClientHello..ServerHello (brick 6 feeds those and `tls_transcript_init`s the stream); this walk folds only the encrypted flight. Built with `-D NETBOOT_TLS_SF` (the composition idiom; `tls_transcript.asm` + `sha256.asm` include'd, org guards inert). Standalone leaf — not in the bootable image. Host-verified (`tls_server_flight_test.go`): the parser recovers the key_share and rejects a wrong cipher / missing key_share / non-1.3 version / HRR sentinel / non-ServerHello type; the walk captures the Finished, sets all four flags, and `SF_HASH_BEFORE_FIN` = Go SHA-256(EE‖Cert‖CertVerify) while a post-walk snapshot = Go SHA-256(the whole flight) — including a variant with a ClientHello..ServerHello transcript prefix.
- `fw_source.asm` — the i100 firmware source: the URL builder + the pinned manifest. `fw_build_path` concatenates the cdn.githubraw.com request path `/<owner>/<repo>/<sha>/<path>` (e.g. `/raspberrypi/firmware/<sha>/boot/start4.elf`) into `FW_PATH` from the configured `FW_OWNER`/`FW_REPO`/`FW_SHA`/`FW_REPOPATH`. cdn.githubraw.com is a plain-HTTP, commit-SHA-addressable proxy (q15 option c) so the SAM fetches an exact pinned revision over plain HTTP (no on-SAM TLS); integrity comes from the SHA-256 verify (the proxy is untrusted). `FW_MANIFEST` is the downloader's file list — the six files from spectrum4's `firmware/Tupfile` at `FW_SHA`, each a record of `{ output-name ptr, in-repo-path ptr, pinned SHA-256, size (32-bit) }`; `fw_manifest_entry` (BC=index → BC=record ptr) walks it. The pinned SHA-256s are the content of each file at this commit — the trusted target the fetch checks the proxy-served bytes against. The size is metadata the downstream consumers need (the picker UI's per-file size, the OACK `tsize` when the object is served, and the record-spanning split count = size ÷ per-record capacity). `fw_plan_path` (BC = file index → that file's cdn path into `FW_PATH`) is the Z80 analogue of `http.Manifest.Plan`'s per-spec `Path` — the per-file fetch loop's "build each selected file's URL" step; it composes `fw_manifest_entry` with the parameterized `fw_build_path_for` (any in-repo path pointer; `fw_build_path` is the fixed-`FW_REPOPATH` wrapper). The spec's other fields come straight off the record (output-name ptr at +0, SHA-256 at +4) plus the `FW_HOST` constant (`cdn.githubraw.com`, mirrors `http.GithubRawHost`). Standalone leaf — not yet wired into the fetch (that brick walks the plan + drives the per-file fetch loop in `http_main`); the bootable image is unchanged. Host-verified vs the Go authorities `http.GithubRawPath` + `http.GithubRawHost` + `http.RPiFirmware` + `http.Manifest.Plan` (`fw_source_test.go`, the FW_* config + manifest records + per-file plan paths read back from the binary — one source of truth); the Go side also re-hashes the real firmware files when present (local dev guard, skipped in CI).
- `body_sink.asm` — the i100 HTTP-header-skip sink adapter (the `bodySink` Z80 port). The filter that sits between the i99 streaming receive (`tcp_conn.asm`'s `storage_sink_flush`) and storage: `body_sink_write` drops the HTTP/1.0 response header (everything up to and including the first `\r\n\r\n`) on the first window, then forwards body bytes whole — so the bytes that reach Trinity storage AND the SHA-256 verify begin at the first body byte (the digest is of the body alone, matching the pinned hash). `tcp_conn.asm` is a pure byte transport with no HTTP knowledge, so the header skip lives here, one layer up. Relies on the header fitting in the first flush window (a window comfortably exceeds any HTTP/1.0 header, so the terminator never straddles two — a chunk with no terminator is dropped and scanning continues, yielding a missing/short body rather than a header leak, byte-for-byte the Go bodySink). Standalone leaf — not yet wired into the fetch (that brick interposes it between the conn flush and the storage sink in the bootable `http_main`); the bootable image is unchanged. Host-verified vs the Go authority `http.NewBodySink` (`body_sink_test.go`, feeding the Z80 port and the Go `bodySink` the same chunk sequence and comparing the forwarded body + per-Write boundaries, incl. the degenerate no-terminator / split-header cases). The port of `http/fetcher.go::bodySink`.
- `fw_span.asm` — the i99/q16 firmware-spanning primitives (the Z80 port of `bdos.SpanPlan`). A multi-MB firmware blob exceeds the SAM's RAM, so it is persisted as a sequence of bounded records (each a plain `HSAVE`) reassembled in order at serve time. `fw_span_chunk_len` is the per-record byte count during streaming — `FW_SPAN_LEN = min(cap, remaining)`, 32-bit (the persist loop seeds `FW_SPAN_REMAINING` = total size, then each pass takes one chunk and decrements until 0; the record count falls out of the loop, so no 32-bit divide). `fw_span_record_name` builds the storage record name `<prefix><NNN>` (the logical name truncated to 7 chars + a 3-digit zero-padded index, a ≤10-char B-DOS name). Standalone leaf — the streaming-persist loop + serve read loop that call these, and the real `RST 8` `HSAVE`/`HLOAD` per record, are the hardware-gated callers; the bootable image is unchanged. Host-verified vs the Go authority `bdos.SpanPlan`/`SpanRecordName` (`fw_span_test.go`: the streaming chunk-length sequence + the record names match byte-for-byte, across non-spanned/spanned/exact-multiple/real-firmware sizes and indices to 999). The port of `bdos/span.go`.
- `tcp_conn.asm` — the i70 TCP connection state machine (client active open): `tcp_connect` originates the SYN, `tcp_conn_recv` dispatches on the connection state (SYN-SENT → SYN-ACK → handshake ACK; ESTABLISHED → ACK inbound data / answer a server FIN with FIN-ACK; FIN-WAIT → the final ACK closes), tracking the 32-bit seq/ack numbers (the one new arithmetic vs the 16-bit UDP loops). Composes `build_tcp_segment` + `encdrv.asm`, host-verified over the i80 emulation byte-for-byte vs `tcp/conn.go::Conn` (`tcp_conn_test.go`). Connection management only — it ACKs inbound data but originates none (the HTTP/1.0 GET rides on top). Inbound body bytes take one of two paths selected by `CONN_SINK_ENABLED` (the port of `conn.go`'s nil-sink check; **default 0 = legacy** accumulate-whole into `CONN_DATA`): set it (with a small `CONN_FLUSH_WINDOW`) to opt into the **i99 streaming sink** — buffer into a bounded window and flush a full window to `storage_sink_flush` as it fills, the partial remainder at the FIN (`conn_flush_final`), so `CONN_DATA` never holds the whole body (the RAM bound for a multi-MB firmware fetch). The wire frames (ACK cadence, seq/ack) are byte-identical either way; the streaming path is host-verified by `tcp_conn_stream_test.go`. `storage_sink_flush` is a **recording test double** here (`CONN_SINK_OUT`/`CONN_SINK_CHUNKS`) — the real B-DOS bounded write to Trinity storage binds there on hardware and is **q16/hardware-gated, out of scope** for this foundation. The streaming sink also carries an **optional SHA-256 verify of the streamed body** (i100, q15 option c): `conn_verify_init` (called once before the body) resets the running hash, `storage_sink_flush` feeds each flushed window through `sha256_update` (so the body is hashed AS it streams, never buffered whole), and `conn_verify_final` writes the digest into `CONN_HASH` and sets `CONN_HASH_MATCH` (1/0) by comparing it against the caller-pinned `CONN_PINNED_HASH`. Host-verified by `tcp_conn_verify_test.go` — the streamed digest byte-matches Go `crypto/sha256` (authority `tcp.HashingSink`) and the verify flag is correct for matching/wrong pins. The verify (`sha256.asm` + the buffers) is **`NETBOOT_HOSTTEST`-only**, like the rest of the streaming sink, so the bootable image carries neither and stays under `&10000`.
- `http_get.asm` — the i70 HTTP/1.0 GET client (firmware self-provisioning): `http_get_start` builds the request `GET <path> HTTP/1.0\r\nHost: <host>\r\n\r\n` and sends it over the established connection (riding `tcp_conn.asm`, which it includes whole); `http_parse_response` parses the accumulated response — the status code and the body offset past the `\r\n\r\n` terminator. HTTP/1.0 so the server closes after the response (the FIN is the end-of-body signal — no chunked/keep-alive). The port of `http/http.go` (`Client.Start` + `ParseResponse`), host-verified over the i80 emulation byte-for-byte (`http_get_test.go`).
- `netboot_http.asm` — **the i70 capstone**, the integrated HTTP fetch phase machine: `http_fetch_first` broadcasts the ARP request, `http_fetch_onframe` drives PH_ARP (ARP reply → learn server MAC → SYN) → PH_HANDSHAKE (the SYN-ACK → the handshake-completing ACK that carries the GET payload, one segment per RFC 793) → PH_RECV (response DATA → ACK + accumulate, server FIN → FIN-ACK → PH_DONE). It `include`s `http_get.asm` whole (→ `tcp_conn` + `build_tcp_segment` + `encdrv`) plus `build_arp_request`, each phase doing its own `drv_read` so the receive phase hands the step straight to the proven `tcp_conn_recv`. Host-verified over the i80 emulation: the ARP/SYN/GET/ACK/FIN-ACK wire frames + the accumulated body match `http/fetcher.go::Fetcher` byte-for-byte (`netboot_http_test.go`). The bootable `http_main` (EEPROM config read + the fetch loop + `http_parse_response` + staging the body into a section-C `STAGING` buffer + the B-DOS HSAVE write-out) runs on real Trinity; the disk is `make netboot-http-disk`. The HSAVE hook dispatch is real-hardware-only (behind `NETBOOT_HOSTTEST`, not host-verifiable); the i93 `bdos_seam` field arithmetic it reuses IS host-verified. The port of `http/fetcher.go`.
- `smoke_test.asm` — **increment 1**, the bring-up smoke test (i94): a bootable program that runs `drv_init` on the real Trinity then answers ARP requests for the SAM's IP — one observable network action confirming the Ethernet path comes up and talks. `smoke_serve_once` is host-verified over the i80 emulation (the ARP reply is byte-for-byte `smoke/smoke.go::Responder.OnFrame`); the bootable `smoke_main` (EEPROM config read + drv_init + the forever loop) runs on real Trinity. The port of `smoke/smoke.go`.
- `dhcp_reply.asm` — build the DHCP OFFER/ACK body the responder (i86) emits (the option template + the fixed option-43 "Raspberry Pi Boot" blob + the echoed client UUID); the port of `dhcp/dhcp.go::BuildReply`.
- `tftp_build.asm` — the i83 TFTP server's reply-packet builders: OACK, DATA, ERROR; the port of `tftp/tftp.go::BuildOACK`/`BuildDATA`/`BuildError`.
- `tftp_parse.asm` — the i83 TFTP server's request side: parse an incoming RRQ (`parse_request`) and resolve its filename against the flat store (`resolve`: 404 serial-subdir, OACK a hit, ERROR(1) every miss); the port of `tftp/tftp.go::ParseRequest` and `tftp/server.go::Resolve`.
- `tftp_client.asm` — the i82 TFTP client's request side: build a read request (`build_rrq`) and parse the server's option-acknowledgement (`parse_oack` + `find_option`, learning the negotiated blksize / file tsize); the port of `tftp/tftp.go::BuildRRQ` and `::ParseOACK`.
- `dhcp_loop.asm` / `tftp_server_loop.asm` / `tftp_client_loop.asm` — the three wire-I/O **transfer state machines** (the i86 DHCP responder, the i83 TFTP server transfer, the i82 TFTP client receive); each composes the primitives above + `encdrv.asm` and runs over the i80 emulation, host-verified byte-for-byte vs its Go authority (`dhcp/responder.go`, `tftp/serverloop.go`, `tftp/clientloop.go`).
- `netboot_serve.asm` — **the serve-files demo** (i96): a focused, bootable "serve a few files to a plain TFTP client" server — **ARP + TFTP only, no DHCP and no Pi PXE blob** — so it is testable from any machine with a stock `tftp`/`curl` client (no Pi, no DHCP). A *new* single-dispatch state machine (`serve_serve_once`): ARP request for our IP → ARP reply; UDP:69 RRQ → serve-by-name (a bare RRQ with no options → DATA block 1 directly per RFC 2347; an optioned RRQ → OACK; a miss → ERROR(1) and keep serving); UDP:our-TID ACK → next DATA. Composes the host-verified `build_udp_frame`/`build_arp_reply`/`tftp_build`/`tftp_parse` + `encdrv.asm` directly. Host-verified over the i80 emulation: ARP + bare-RRQ DATA + optioned-RRQ OACK + miss-ERROR(1) match `serve/serve.go::Responder.OnFrame` byte-for-byte (`netboot_serve_test.go`). The bootable `serve_main` (EEPROM config read + the baked-in demo files `hello.txt`/`readme.txt` + the forever loop) runs on real Trinity; the disk is `make netboot-serve-disk`. The port of `serve/serve.go`.
- `netboot_server.asm` — **increment 2**, the integrated netboot server (i95): a *new* single-dispatch state machine (`netboot_serve_once`) that reads one frame and routes it — ARP request for our IP → ARP reply, UDP:67 DISCOVER/REQUEST → OFFER/ACK, UDP:69 RRQ → OACK/ERROR(1) (arm the transfer), UDP:our-TID ACK → FirstData/next DATA — composing the host-verified builders/parsers + `encdrv.asm` directly (it does NOT `include` the standalone loop files, which would collide on `RXBUF`/`CONFIG_*`/`build_udp_frame`/`encdrv`). Host-verified over the i80 emulation: a full DISCOVER→OFFER→REQUEST→ACK→ARP→RRQ→OACK→ACK→DATA session matches `server/server.go::Server.OnFrame` byte-for-byte (`netboot_server_test.go`). The bootable `netboot_main` (EEPROM config read + a fixed DHCP pool + the forever loop) runs on real Trinity; the disk is `make netboot-server-disk`. The port of `server/server.go`.
- `netboot_client.asm` — **increment 3**, the TFTP client boot disk (i82): a bootable program that fetches a file (a `.mgt` disk image) from a TFTP server and writes it to Trinity storage via the B-DOS hooks. A *new* phase machine (`client_first` broadcasts the ARP request; `client_run_once` steps PHASE_ARP → learn server MAC + send RRQ → PHASE_XFER → accumulate DATA / send ACKs → short final block ends it, stray-TID DATA → ERROR(5)), composing the host-verified `build_udp_frame`/`build_arp_request`/`tftp_client` (build_rrq) + `bdos_seam` + `encdrv.asm` directly (NOT `include`ing the standalone front/loop files — symbol collisions). Host-verified over the i80 emulation: the ARP request + the RRQ + the ACK cadence + the accumulated staging bytes match `client/client.go::Client` byte-for-byte (`netboot_client_test.go`). The bootable `client_main` (EEPROM config read + the fetch + the B-DOS HSAVE write-out) runs on real Trinity; the disk is `make netboot-client-disk`. The HSAVE hook dispatch is real-hardware-only (behind `NETBOOT_HOSTTEST`, not host-verifiable); the i93 field arithmetic it uses IS host-verified. The port of `client/client.go`.
- `tftp_client_front.asm` — the i82 client's **request-origination front** (the step before the receive loop): `tftp_send_arp` broadcasts an ARP request, `tftp_recv_arp` learns the server MAC from the reply, `tftp_send_rrq` sends the RRQ; the port of `tftp/clientfront.go::ClientFront` (+ `frame.ParseARPReply`).
- `bdos_seam.asm` — the **storage seam**: the UIFA/DIFA field arithmetic (`bdos_name_to_uifa` / `bdos_difa_to_size` / `bdos_fill_save_uifa`) that glues the i83 server (serve a file by name) and the i82 client (write a received file by name) to the B-DOS hooks; the port of `bdos/bdos.go`. The field maths is host-verifiable; the RST 8 hook dispatch (HGTHD/HLOAD/HSAVE/HRECORD, behind `NETBOOT_HOSTTEST`) is **not** host-verifiable (no ROM/SAMDOS in the harness) and stays gated on real Trinity.
- `encdrv.asm` — the vendored Quazar Trinity ENC28J60 driver (simonowen/trinload, Simon Owen, verbatim): the real wire-I/O `drv_init`/`drv_read`/`drv_write` the netboot stack sits on. Not reimplemented (port/reuse the authority). `encdrv_harness.asm` orgs it at `&8000` so the i80 emulation can run it.
- `eeprom.asm` — the vendored Quazar Trinity EEPROM library (Colin Piggot, via simonowen/trinload, verbatim): `find_index` + `read_chunk` read the "Trinity Network " flash chunk so a bootable program (the smoke test, later the server/client) uses the SAM's real MAC + IP on hardware. NOT host-verifiable (no EEPROM behind port `&DD` in the harness; the chunk's `sam_ip` offset is a flagged hardware unknown, plan §7.5 #4) — real-Trinity path only.
