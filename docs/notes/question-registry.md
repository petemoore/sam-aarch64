# Question index — the project-wide `qN` registry

This is the **canonical, milestone-neutral registry** of every **open question for
Pete** (decisions an agent cannot settle itself, or chose to defer rather than
guess). It is the sibling of the item registry (`docs/notes/item-registry.md`): the
item registry tracks *work* (`iN`), this tracks *unresolved decisions* (`qN`).

**Governance is identical to the item registry — see `docs/notes/item-registry.md`
for the shared registry discipline** (stable ids locked once assigned, never
renumbered, never archived, marked-resolved rather than deleted). In one line for
questions: `qN` ids; the table is the **single sure-fire list of what's still open**;
add the moment a question arises (not just in chat — chat questions get lost in
simultaneous-edit races); flip ⏳→✅ with the resolution + where it was decided the
instant it's answered; land on `main` via PR so Pete sees it where he reads.

This doc is **never archived**: when a milestone status doc is superseded, its
questions live on here, so an open question is never stranded in an archived
`m{N}-status` doc. (Created 2026-06-08 by extracting the `qN` list out of
`https://github.com/petemoore/sam-aarch64/blob/c0f62fa/docs/notes/m7-status.md` — mirroring the i*N* item-registry extraction in PR #128 — because
M7 was winding down while open questions like q1 were still live. See the

| **q16** | **How does the netboot fetch write a multi-MB body to Trinity B-DOS storage incrementally?** (i99 design pass, 2026-06-15 — a genuine B-DOS-internals decision, surfaced by a real doc contradiction, not a manufactured blocker.) The streaming RAM-side (bounded buffer → abstract sink) is autonomous-eligible and proceeds regardless; this `qN` is only the **real-hardware binding** of that sink. The project's **SAMDOS-2-source audit** (`docs/notes/sam-stub-audit.md` bugs #1–#3) finds the byte-stream append hooks `HOFLE`/`HSBYT`/`HCFSM` **broken for external `RST 8` callers** (they assume `IX=dchan`, only set on the high-level HSAVE path), leaving whole-file `HSAVE` as the only *verified* write path — but HSAVE (a) needs the whole file contiguous in RAM (impossible for multi-MB) and (b) **can't encode >64 KB** in its UIFA length (i24). Yet `docs/notes/bdos-trinity-fork-analysis.md:41` asserts "HRECORD then ordinary HSAVE/HOFLE+HSBYT writes" as viable — an inference the i62 dual-run never exercised (it tested only HSAVE/HGTHD/HLOAD). **The two contradict; resolving needs Pete's off-repo B-DOS 1.5t analysis (`~/sam-archive/bdos/analysis/`) + his B-DOS knowledge.** Candidate bindings: **(a)** `HOFLE`+`HSBYT` incremental append (needs the 1.5t analysis to confirm B-DOS permits the external-caller path SAMDOS-2 breaks, maybe with an `IX=dchan` pre-setup); **(b)** raw-sector `HWSAD` streaming with the file header / sector-map / directory entry synthesised on the Z80 (powerful but re-implements B-DOS FS internals); **(c)** a convention of multiple **bounded** HSAVEs (each ≤64 KB, spanning records, reassembled at serve time) — the simplest, stays on the *verified* HSAVE hook, at the cost of a naming/spanning convention. Agent leans **(c)** as the lowest-risk default (verified hook only) pending Pete. **Non-blocking** — the host-verifiable streaming receive + abstract sink + tests proceed now; only the real flush is gated here. **✅ RESOLVED — Pete, 2026-06-15: option (c), multi-record/disk spanning via bounded `HSAVE`s.** Persist the firmware as a sequence of bounded files spanning multiple Trinity records/disks (each record ≈ one ~800 KB floppy image; a multi-MB blob spans several), each written with a plain `HSAVE` (the *verified* hook) and reassembled in order at serve time. So the binding constraints are **RAM** (the HSAVE source can't hold multi-MB → stream, i99) + **per-record capacity** (~800 KB → span records), NOT a 64 KB file limit; the streaming window can be comfortably large (bounded by RAM + the record size).
