## START HERE — session handover protocol (read this first)

**This file is the canonical entry point and the agent→agent handover contract.** If you are an agent picking up this project: read this section, then the **"Current State"** block below, then the current milestone status doc, then the project memory index (auto-loaded at session start). That is the complete start-up read — everything else is reached via links from here.

### The contract (always inherited, always maintained)

1. **Tracking is part of "done" — and it happens at REQUEST time, not PR time.** The moment a piece of work is well-defined *and* you have sign-off to do it, create its `iN` row in `registry/items.yaml` (or `qN` in `registry/questions.yaml`) **before you start implementing** — `build/registry add …` (the id is auto-allocated; there is no `next-id`, no `--id`) then `make registry`, committed **locally** (no separate PR/merge dance just to capture): the item you are working rides **its feature branch** — cut from `origin/main`, CLAUDE.md §4 — and any *other* captured ask commits on **local `main`** (reconciled at the wind-down sweep), so unrelated IN_PROGRESS markers never leak into PRs (i342). Mark it **`IN_PROGRESS`** and **say so out loud**: "logged as iNNNN, marked IN_PROGRESS, now working on it." So intent survives a crash mid-work, and many parallel asks become many `IN_PROGRESS` rows — **a feature, not a violation: the registry is the session's completeness ledger** (query `build/registry in-progress` at wind-down — see hygiene). IN_PROGRESS is **transient and session-local — `main` never carries it**: before a PR **merges**, resolve every entry (DONE for finished work, `split` into a DONE part + a fresh OPEN part for partial, or back to OPEN if untouched), so what lands on `main` is *resolved* states (DONE/OPEN), never a wall of IN_PROGRESS. (A fleeting IN_PROGRESS commit may sit in a feature branch's history — a self-completing PR can't know its own number before the first push — but the merged result is always clean; that's the light, watertight line, no history-rewrite gymnastics.) A PR completes the IN_PROGRESS items it finished — and **one PR may complete several** (an item is one deliverable; a PR is one cohesive reviewable change). Treat a missing tracking entry like a missing test: reviewers flag it. **This is the agent's responsibility, never Pete's** — including for work you merely *raise* with him: asking "should we do X later / in a future session?" does **not** delegate tracking to Pete. Track X the moment you raise it (a future-session item is still an item); a question *to* Pete is itself a `qN`. Pete is not your tracker.
2. **One home per kind of thing** (this is how the docs stay un-sprawled):
   - **ROADMAP.md** (this file) — the index and the live "Current State" below.
   - **Item registry** — source: `registry/items.yaml`; generated views: `docs/notes/item-registry-open.md` + `item-registry-closed.md`. The project-wide, milestone-neutral `iN` id↔item map. A fresh agent reads the **open** view for outstanding work. The YAML is the source of truth — never hand-edit the generated `.md` (the `registry-sync` CI job fails if you do). Resolve an item with `build/registry set-status --id iNN --status DONE --pr N` then `make registry`, in the completing PR.
   - **Question registry** — source: `registry/questions.yaml`; generated view: `docs/notes/question-registry-open.md`. Questions are **transient**: every question for Pete goes into the YAML the moment it arises (`build/registry add --space questions …`); answering one means curating every dependent item (apply the decision), then deleting the question (`build/registry answer --id qNN`). There is no closed-questions view — the decision lives in the items + git history.
   - **Backlog** — `docs/notes/backlog.md` (generated from `registry/priority.yaml`). The priority-ordered list of open pullable items; `build/registry ready` returns the unblocked tip. This **supersedes** the prose "proposed implementation sequence" as the single source of work ordering.
   - **Milestone status docs** (`docs/notes/m{N}-status.md`) — the per-milestone source of truth.
   - **Memory** (`~/.claude/projects/.../memory/`) — cross-session preferences, facts, feedback. *Not* work-tracking.
   - Superseded docs are **deleted** — git history is the archive; pin citations to a blob link if a living doc must cite one.
3. **At milestone close**, walk the item registry and ask of each item: still deferred, or does it now fold into the milestone in flight? **The `iN` item registry and the `qN` question registry are both milestone-neutral and never archived:** at milestone close, every item belonging to that milestone must be marked `DONE`/`WONTFIX` (via `build/registry set-status …` then `make registry`) or migrated (re-pointed) to the active milestone's strands — no item may be left living only in a closing `m{N}-status` doc. Open questions for Pete live only in the question registry (`qN`) for the same reason. **The milestone status doc is deleted at close** (git history is the archive) after the registry walk completes.
4. **Delegate to subagents to preserve orchestration context.** The agent driving a session (the *orchestrator*) should push self-contained, well-scoped work out to subagents — codebase searches, mechanical edits, doc drafting, focused investigations, even whole low-risk PRs (implement → verify locally → commit → push → open PR) — via the `Agent` tool (and `Explore` / `Plan`), keeping only the conclusions in its own window. A subagent's full transcript is discarded; only its final summary returns, so the orchestrator's context lasts far longer. The orchestrator keeps the judgement calls itself: sequencing, monitoring CI, merge/launch decisions, and anything user-facing. The durable state lives in subagents-plus-these-docs, not in any one agent's window — so when context *does* fill, the handover (update "Current State", below) lets the next agent resume as orchestrator with nothing lost. Prefer launching independent subagents in parallel (one message, multiple `Agent` calls) when the work has no shared state.

### Session hygiene (the minimal ritual)

- **Continue vs wind down at a `/context` checkpoint:** the decision rule lives in **one** place — the `tools/autonomous-loop/monitor.sh` task-done nudge (`RESUME_NUDGE`), delivered at the decision point. Don't re-litigate it; follow the nudge. (It was i104's top friction — ~9 sessions re-litigated it — which is *why* the rule is encoded at the point of use, not restated here.)
- **Closing a session:** **no magic words** — *any* wind-down phrasing ("close the session", "let's wrap up", "prepare for handover", "goodnight, what's next?") triggers this. The agent then updates the **"Current State"** block below *in place* — what landed, what's in flight (open PRs / branches / running agents), key decisions/gotchas, and open Pete-questions — obeying the **lean state + pointers** discipline stated in that block's preamble (no accreted context, no work-ordering). The agent also confirms tracking is current (rule 1) and leaves the working copy on a clean, current `main`. Do **not** write a new dated handoff doc — update the standing block. **Commit this update directly to `main`** (it is doc-only — CLAUDE.md §4); don't leave the live state stuck in an open PR, or the next session reads stale context.
- **Before a PR merges — and at wind-down — reconcile every `IN_PROGRESS` item** (IN_PROGRESS is transient and never reaches `main`; rule 1). Run `build/registry in-progress`; for each row it lists, exactly one of: it is genuinely DONE (its PR merged → `set-status … --status DONE --pr N`); or you finished *part* of it → **`build/registry split`** the done part off as a DONE child and leave the rest a fresh OPEN child (capturing the true partial state); or it was untouched → set it back to `OPEN`. The list must end holding only what is *actually* still in flight. This is the completeness check that guarantees no signed-off ask was lost in the chat scroll (rule 1 / i154).
- **At wind-down, also write a per-session retro report** to `~/claude-retro/` (item i104): a short, blameless, *independent* note (don't read other sessions' reports first) on genuine process friction this session — *say what genuinely happened: no manufactured problems, no suppressed ones*; **"nothing notable" is a valid, good report**; ground each friction in a specific incident. Format + rationale: `~/claude-retro/README.md`.
- **Starting a session:** the standard start prompt is just **"Continue per docs/ROADMAP.md."** A SessionStart hook (`tools/session-handover.sh`) runs first: it surfaces this section and, **when you are on a clean `main`, auto-`fetch`es and fast-forwards to the latest** so the doc you read is current. If it instead **warns** (you are on a feature branch, have uncommitted changes, or `main` can't fast-forward), refresh deliberately before relying on the doc: stash/commit your work, then `git checkout main && git pull --ff-only`. Then read this section → Current State → resume; no bespoke per-session prompt is needed.

## Vision

A SAM Coupé Z80 program that hosts a complete aarch64 development workflow — editor, assembler, disassembler, TFTP shipper — and produces byte-identical binaries to GNU `aarch64-none-elf-as` for the spectrum4 kernel. Daily-driver SAM-as-development-machine for Raspberry Pi 400 bare-metal work.

See `docs/specs/vision.md` for the long-form pitch and `docs/specs/phase1-assembler.md` for the Phase 1 (assembler) shape.

## How to extend this doc

When new deferred work or a design decision arises:
1. Add an `iN` row via `build/registry add --title "…" --desc "…" --status OPEN --owner agent` (the id is auto-allocated; add `--space questions` for a `qN`; use `build/registry split --parent iNN --title "…" …` for a sub-item — its id is determined from the parent), then `make registry`. Commit the YAML and regenerated `.md` together. That is the one home — do not add a checklist here.
2. Add the new design note to the appropriate table above (milestone, or "Design notes not strictly inside a milestone") and link it from `docs/specs/README.md` if it lives under `docs/specs/`.

The goal: no design discussion is ever lost to context drift. If it's worth writing down, it's worth a registry row.
